Release History

What changed, and
why it changed

Every version of the MCAgents plugin, newest first. Each entry explains what moved and what it means for a server operator, so upgrading is a decision you can make from this page rather than from a diff.

How versions work

Every module of the plugin shares one semantic version, so a single number describes the whole build. The first number changes when something incompatible changes, the second when a feature is added, and the third when a fix lands. A version marked In review is proposed and open for review; it is not on the default branch yet, so it is not something to install.

3.1.0 In review

One jar for every server. Until now, installing the plugin meant choosing the download that matched your server software, and choosing wrong failed at startup.

A universal build

A new build detects whether it is running on SpigotMC, PaperMC, or FoliaMC when the server starts, then installs the scheduling and extension behaviour that server needs. The same file works on all three.

The single-server builds remain

The three per-platform downloads are still produced for anyone who prefers a smaller artifact aimed at one server. Nothing about them changes.

Adding a platform got cheaper

What differs between servers is now one small object rather than a whole startup sequence, so supporting a new server means writing that object — not another copy of the plugin.

3.0.0 In review

A tidy-up of what the project publishes, and the end of a long-standing duplication between the three server builds.

Only the libraries are published

The four library pieces — the contracts, the tool interface, the data and workflow layer, and the shared server core — are what other projects depend on, so they are what gets published. The runnable server builds are downloads, not dependencies, and are no longer pushed to the package registry.

One startup sequence, not three

Each server build carried its own copy of the same startup code, and the copies had already drifted apart. They now share one sequence and keep only what genuinely differs, which removes over five hundred lines of duplication.

MySQL became selectable

A MySQL storage backend had been written but was never reachable from the configuration file. It can now be chosen like any other backend, and the shipped configuration documents it.

2.0.0 In review

A structural change: one clear way in, instead of several. Nothing an operator configures changes, but anyone writing an extension against the plugin will notice.

A single entry point

Storage and the AI workflow are reached through one class. Previously each server build assembled its own database connection and every AI call carried its own client, so the same responsibility lived in several places at once.

The boundary is enforced

A test reads the server-side code and fails the build if anything reaches around that entry point. The rule is checked rather than remembered, so it holds as the project grows.

Documented in full

Every class, field, and method across the four library pieces carries documentation, and every package explains what it is responsible for. The generated API documentation builds without a single warning.

For extension authors

Calls that used to pass a client no longer take one, and the plugin is obtained through a factory rather than constructed directly. Both are small edits, and both are why this is a major version.

1.0.0 Current

The first assembled release: the whole framework in one build, with the core features that used to ship as a separate extension folded into the plugin.

Talking to an agent

The /ai command in two modes — one-off questions, and a continued conversation that remembers the session. Players and the console both use it.

Tools with permissions

Built-in tools for tokens, platforms, and models, each checking who is asking before it acts. Extensions register their own tools the same way.

A staged tool workflow

Instead of sending every tool on every request, the agent narrows down by category, then by name, and only then receives full tool definitions — which keeps token spend low.

Choice of storage

Data lives in a local file database by default, or in PostgreSQL, MongoDB, or the shared central server when several servers should see the same accounts and history.

Reusable prompts

Prompts can be saved and re-run by id, either as server-wide entries or as a player's own, and can be pinned to a fixed set of tools.

Automated testing

The /ai tester command replays saved prompts against a dedicated account and writes a report for each run, so the workflow can be checked without playing through it.
